# #678 第三轮 — `zoom: 0.75` 到底做了什么，以及它炸掉了我上一条的哪个建议

**2026-07-31，真 Chromium 实测。** 探针：[`zoom-probe.mjs`](zoom-probe.mjs)、[`cqh-probe.mjs`](cqh-probe.mjs)。

---

## 1. `818.182px` ⇒ 测量时的视口高是 **2045px**，不是 900px

反解实测（`zoom` 取任意值都不影响这一列）：

| 视口高 | `40vh` 的 computed |
|---|---|
| 900 | 360px |
| 1534 | 613.6px |
| **2045** | **818px** ✅ |
| 2045（zoom=0.75） | **818px** — 一模一样 |

`818 / 0.4 = 2045`。所以那次控制台测量的窗口约 2045px 高（4K 屏满窗很接近这个数），
**和截图那个 900px 的窗口不是同一次**。

→ 「818 = 900 的 91%」这个换算用错了分母。在 2045px 的窗口里，818px 就是**正好 40%**。

## 2. `zoom` 对 `vh` 的作用方向和预期相反 —— 它不放大上限，它缩小渲染

实测（视口 900）：

| zoom | computed `max-height` | 实际渲染（视觉 px） | 占视觉视口 |
|---|---|---|---|
| 1 | 360px | 360 | 40.0% |
| **0.75** | **360px**（不变） | **270** | **30.0%** |

`vh` 确实不受 zoom 影响 —— **你这一半是对的**：computed 值恒等于 `0.4 × 真实视口高`。
但那个值是**局部坐标系**的 px，整个子树再乘 0.75 渲染出去。
所以 `max-h-[40vh]` 在 `zoom:0.75` 下**渲染成 30vh —— 比原意更紧，不是更松**。

### 所以 ② 那条推翻不成立

「真实上限是 91%，面板可以长到几乎满屏」→ 实测渲染上限是视觉视口的 **30%**。
加上按钮行和边框（也被 zoom 缩），面板视觉总高约 **33~38%** 视口。

**我上一条的结论反而更稳了**：`R=0.5` 在这两种情形下都永远迈不过去 ——
现状（上限 30vh）和修好之后（真 40vh + 按钮行 ≈ 45%）都不到 50%。
上一条那些落点表格不用重算，因为它们是按视觉 px 量的，量尺没变。

### 但 ① 里有个真东西：你在混两套坐标系

「818px 上限 vs 面板 290px」—— **818 是局部 px，290 是从截图量的视觉 px**。
换算过去：290 视觉 = 387 局部。在截图那个 900px 窗口里，上限是 360 局部 = 270 视觉。

| | 局部 px | 视觉 px |
|---|---|---|
| 上限（900px 窗口） | 360 | 270 |
| 建议区内容（截图） | ~300 | ~225 |

**余量只有 1.2 倍，快顶到了。** AI 再多吐两条建议就会触发滚动。
所以"没看到滚动条"不是因为上限大到没用 —— 是刚好差一点。

## 3. ⚠️ 更严重：我上一条推荐的手写 `scrollTop` 数学在 `zoom` 下差 25%

实测（视口 900，容器内滚动到目标）：

| zoom | 容器 rect 高 | 容器 clientHeight | 想滚 | 赋给 scrollTop | **手写残差** | `scrollIntoView` 残差 |
|---|---|---|---|---|---|---|
| 1 | 540 | 538 | 1501 | 1501 | **0px** | 1px |
| **0.75** | **405** | **537** | 1126 | 1126.7 | **281px** | 1px |

`281 / 1126 = 24.96%` —— 正好 `1 − 0.75`。

根因：**`getBoundingClientRect()` 返回视觉 px，`scrollTop` 吃的是局部 px。**
我上一条给的
`sc.scrollTop += (r.top - bandTop)` 把视觉差值赋给了局部属性，**在 zoom 子树里恒定少滚 25%**。
`scrollIntoView` 是浏览器原生的，坐标系自洽（残差 1px）。

### 这很可能就是第 0 节那个 182px 之谜

`728 × 0.25 = 182`。如果定位代码里有任何一处把 rect 派生的差值喂给
`scrollTop` / `scrollBy` / `scrollTo`，而本该滚 728px，就会正好停在低 182px 的位置。

**判定：grep 定位函数里有没有 `scrollTop`/`scrollBy`/`scrollTo` 接收 rect 派生的值。**
有 → 就是它，除以实测 zoom 系数即可。没有 → 回到上一轮的原因 1（滚动压根没跑）。

### 单位规则（这一版要写进代码注释）

| 坐标系 | API |
|---|---|
| **视觉 px**（已含 zoom） | `getBoundingClientRect()`、`window.innerHeight/innerWidth` |
| **局部 px**（未含 zoom） | `scrollTop`、`clientHeight`、`offsetHeight`、`scrollHeight`、`getComputedStyle()` |

**两套绝不能相减。** 运行时取实测 zoom 系数，不要写死 0.75：

```js
const z = el.getBoundingClientRect().height / el.offsetHeight;  // 累积有效 zoom
sc.scrollTop += visualDelta / z;                                 // 视觉 → 局部
```

## 4. ③ 换单位：`cqh` 和 `%` 都没用，实测三者完全相同

| 单位 | zoom=1 渲染 | zoom=0.75 渲染 | 占视觉视口 |
|---|---|---|---|
| `40vh` | 360 | 270 | 30% |
| `40cqh`（容器 `container-type:size`） | 360 | 270 | 30% |
| `40%`（父容器高度确定） | 360 | 270 | 30% |

原因：容器本身就在 zoom 子树内，它的局部高度已经是未缩放值，
取 40% 之后再整体乘 0.75 —— 换任何 CSS 单位都躲不开这个乘数。**所以 CSS 路线走不通。**

### 先回答一个问题，再选方案：**这个 40% 是相对谁的 40%？**

- **相对滚动栏** → 现状已经是对的（613.5 视觉 / 1534 视觉栏高 = 40%），**什么都不用改**
- **相对整屏可视高度** → 只能 JS 现算，和处理导航偏移同一个手法：

```js
const z = box.getBoundingClientRect().height / box.offsetHeight;
const bandVisual = bandBottom - bandTop;        // 视觉 px，从浮层实测下沿算
box.style.maxHeight = (0.4 * bandVisual / z) + 'px';   // 转成局部 px 再写
```

固定 `max-h-[360px]` 不推荐 —— 你说的小屏问题之外，它在 2045px 窗口上只有 17%，两头都不讨好。

⚠️ **顺带**：`height: 100vh` 在 `zoom:0.75` 下渲染成视口的 75%，栏底会短一截。
你说 `index.css:101-119` 已经吃过这个坑并有对策，那这条大概已经绕过了 ——
但我这边没有那份代码，**请确认那个滚动栏用的是绕过后的写法**，
否则我第二轮算的「可视带」下沿会比真实短 25%。
