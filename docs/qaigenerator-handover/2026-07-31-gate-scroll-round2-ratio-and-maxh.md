## 0. ⚠️ 先看这个：截图显示的不是「居中偏低」

| | y |
|---|---|
| 面板实测（截图） | 520 → 810，高 290，中心 **665** |
| 可视带中心 | **483** |
| **如果真的居中了，面板顶应在** | **338**（实测值，见下表） |

面板顶实测 **520，比"居中"低 182px**。`block:"center"` 会把面板推**高**，不会推低。
所以现在这个位置**不是居中造成的**。在给 ② 换判据之前得先弄清它为什么在那儿 ——
否则是在改一个不存在的症状。

### 候选原因（按可能性排序，都可判定）

| # | 原因 | 数字是否吻合 | 判定方法 |
|---|---|---|---|
| **1** | **滚动根本没执行**（ref 没挂上 / 调用时 element 还是 null / 用了 `window.scrollTo` 而真正的滚动容器是内层栏） | ✅ 完全吻合。截图里滚动条滑块靠近顶部，说明容器 `scrollTop` ≈ 0，压根没滚 | 在定位函数里打一行 `scrollTop` 的前后值；或看 ref 是否非 null |
| **2** | gate 目标是**整个 Q2 字段组**（~465px）而非建议面板，且滚完之后才长高 | ✅ 吻合。实测该场景下移上限 **+209px**，观测 +182 落在区间内 | 打印 `scrollIntoView` 目标元素的 `getBoundingClientRect()` |
| 3 | 建议面板自身（290px）滚完才长高 | ❌ **数字不够**。实测下移上限只有 **+121~145px** < 观测 182 | 已排除（作为唯一原因） |
| 4 | `block:"center"` 落点本身偏低 | ❌ 方向相反。居中会落在 y=338，比观测**高** 182px | 已排除 |
| 5 | 容器已到 `scrollHeight - clientHeight` 滚不动 | ❌ 与滑块靠顶部不符 | 比较 `scrollTop` 与上限 |

**原因 1 和 2 都指向同一个动作**：在定位函数里把「目标元素的 rect」和「容器 scrollTop 的前后值」
打出来，一次就能定案。这个比调阈值优先。

## 1. `max-h-[40vh]` 到底生效没有

**答案：截图这个观测判定不了 —— 你的第一个猜测在几何上完全自洽。**

建议文本区在截图里约 `y 550→775 = 225px`，40vh 在 900px 视口 = **360px**。
`225 < 360` → **没超上限，本来就不该有滚动条**。所以"没滚动条"这件事，
在 class 接上和没接上两种情况下**观测完全相同**：

| 视口高 | `max-h` | 40vh | 面板高 | 内部滚动 |
|---|---|---|---|---|
| 900 | 接上 | 360px | 290 | 无 |
| 900 | **没接** | 360px | 290 | 无 |
| 400 | 接上 | 160px | **208** | 有 |
| 400 | **没接** | 160px | **290** | 无 |

900px 视口两行一模一样；**400px 视口才分得开**（面板高 208 vs 290）。

### 判定方法（二选一，都是只读）

```js
// A. 控制台一行 —— 最直接
getComputedStyle(document.querySelector('<建议区选择器>')).maxHeight
// 返回 "none"    → class 没接上
// 返回 "360px"   → 接上了（应约等于 0.4 × 视口高）
```

```
// B. 回归测试：把视口压到 400px 高，断言建议区 clientHeight <= 0.4*视口高 + 1
//    这条能同时钉住"接上了"和"以后别被改掉"
```

## 2. ⚠️ `R = 0.5` 这个阈值是空转，永远不会触发

实测（变体 B，1920×900，可视带 `[66,900]`，`ratio` 策略 = 超过比例则顶部对齐+24px 边距）：

| 面板高 | 占视口 | `center`（现状） | `ratio R=0.5` | `ratio R=0.32` | `topAlways`（建议） |
|---|---|---|---|---|---|
| 180px | 20% | `[393,573]` 上空 327 | `[393,573]` ← **同 center** | `[393,573]` ← 同 center | `[90,270]` 上空 24 |
| **290px**（截图实际） | **32%** | `[338,628]` 上空 272 | `[338,628]` ← **同 center** | `[90,380]` 上空 24 | `[90,380]` 上空 24 |
| 465px（整个 Q2 组） | 45% | `[279,687]` 上空 213 | `[279,687]` ← **同 center** | `[90,498]` 上空 24 | `[90,498]` 上空 24 |

三种高度下 `R=0.5` 的落点**与现状逐像素相同**。原因：

- 截图面板 290px = 视口的 **32%**
- 即使 gate 目标是整个 Q2 组（~465px）也只有 **45%**
- 而 ③ 的 `max-h-[40vh]` 把面板锁在 **≤45%**（40vh + 按钮行 44 + 边框 4）

→ **50% 的门槛在 `max-h` 存在的前提下永远迈不过去。** 改了等于没改，
而且又多一条永不执行的分支 —— 和上一轮 `nearest` 那条死代码同一个坑。

### 想让阈值真的触发，得低于 45%；但压线很脆

`R=0.32` 能让 290px 的面板顶部对齐。可是**面板正好是 32%，阈值 0.32，压在线上** ——
AI 这次返回 6 条建议、下次返回 5 条或 7 条，面板高度就跨过阈值，落点策略随之翻转。
**"页面怎么滚"取决于"AI 这次吐了几条"**，这不是一个能维护的判据。

### 建议：取消阈值，恒顶部对齐

`topAlways`（边距从导航条实测下沿算）在**所有**高度下都是：上空 24、顶部被盖 0。
一条路径、没有阈值、没有死分支、不受建议条数影响，而且顺手解决了上一轮
「级别2 是不是死代码」那个悬案 —— 因为不再有级别之分。

## 3. 高面板（你要的第三种）以及导航偏移核实

关掉 `max-h` 才做得出真正的高面板。变体 B，可视带 `[66,900]`：

| 面板高 | 策略 | 面板 y | 上空 | **顶部被导航盖住** | 按钮出界 |
|---|---|---|---|---|---|
| 600 | `center` | `[183,783]` | 117 | 0 | 0 |
| 600 | `topAlways` | `[90,690]` | 24 | **0** | 0 |
| 900 | `center` | `[33,933]` | −33 | **33** | 33 |
| 900 | `nearest` | `[66,966]` | 0 | 0 | 66 |
| 900 | `topAlways` | `[90,990]` | 24 | **0** | 90 |
| 1100 | `center` | `[-67,1033]` | −133 | **133** | 133 |
| 1100 | `nearest` | `[66,1166]` | 0 | 0 | 266 |
| 1100 | `topAlways` | `[90,1190]` | 24 | **0** | 290 |

**导航偏移核实通过**：`topAlways` 因为边距是从 `nav.getBoundingClientRect().bottom` 现算的，
在每一种高度、两种布局变体下「顶部被盖」都是 **0**。而 `center` 在面板高于可视带时
会把顶部塞到导航条底下（900px 面板盖 33、1100px 盖 133）。

⚠️ **但面板真的高过可视带时，三种策略都保不住按钮**（出界 90 / 266 / 290px）。
和上一轮结论一致：**这种情况唯一的解是让面板装得下**，不是换落点。
`max-h-[40vh]` 已经做到了这一点 —— 只要它真的接上了（见第 1 节）。

## 4. 建议的收尾顺序

1. **先定案第 0 节**：打两行日志，确认滚动到底跑没跑、目标元素是谁。这决定 ② 要不要改
